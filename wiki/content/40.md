# Batch

A **Batch** project runs one chain of ComfyUI workflows over and over, once for each set of values you give it. Instead of generating an image, turning it into a mesh and texturing it by hand — then repeating all of that for the next character — you describe the chain once and hand it a list.

Pick **Batch** as the preset when you create a project. It opens straight into the batch workspace instead of a Kanban board or a Graph.

> Batch runs **ComfyUI workflows only**. The external mesh APIs (Tripo, Tencent, Hitem3D) are not available as stages, because they return results by polling rather than in one pass.

## How it fits together

The workspace reads left to right:

| Column | What it holds |
| --- | --- |
| **PARAMETERS** | The **variables** you declare, and the **groups** that fill them |
| **STAGE 1, 2, 3…** | One ComfyUI workflow each, run in order |

Two rules drive everything:

- **A group is one run.** Three groups means the whole chain runs three times.
- **A stage runs once per group**, and can consume the output of any earlier stage in the same run.

So three groups and five stages is fifteen executions — the toolbar shows exactly that: `3 groups · 5 stages · 15 runs`.

## Variables and groups

A **variable** is declared once for the whole batch, under **VARIABLES**. Give it a name of your choosing and a type. The name is how you will recognise it later, so `prompt`, `name` or `target face number` beats `var1`.

| Type | What a group supplies |
| --- | --- |
| **string** | Any text — a prompt, a label |
| **number** | A number — a face count, a resolution |
| **boolean** | A true/false toggle — PBR on, quad topology off |
| **image** | A picked image, fed straight into an image input |
| **mesh** | A picked mesh, fed straight into a mesh input |

Each **group**, under **GROUPS · ONE RUN EACH**, is one row of values for those variables. Name the group after what it produces (`Anime Sorceress`, `Anime Warrior`) — that name labels its row in the results.

A group does **not** have to fill in every variable. Leave a value blank and that run falls back to whatever the stage has set manually. This is what lets one group override the texture resolution while the others use the stage default.

A **boolean** variable is set from a three-way dropdown — **True**, **False**, or *fallback to stage value* — rather than a checkbox. `false` is a real value, so an unticked box could not be told apart from a group that simply does not set it.

Use the **copy** icon on a group to duplicate it with its values, then change just the one field you care about.

### Image and mesh variables

An **image** or **mesh** variable is not typed in — each group picks a file for it, from a dropdown with two sources:

| Source | Where it comes from |
| --- | --- |
| **From Assets** | Anything in your asset library, including edits and versions |
| **Local Computer** | A file from disk, uploaded into this project |

The picked file appears as a small chip with its thumbnail; the **×** clears it and the dropdown swaps it for another. Whatever you pick becomes part of the project, so it behaves like any other asset from then on.

This is what lets a batch **start** from files you already have — twenty product photos, or twenty meshes to retopologise — instead of only from something an earlier stage generated. A result derived from a picked mesh is filed as a **version of it**, exactly as it would be mid-chain.

Changing a variable between a file type, a boolean and a text/number one clears the values groups already hold for it — a prompt is neither an image nor a toggle.

## Stages

Each stage picks one **ComfyUI workflow**, then decides where each of its parameters comes from.

### Result name

The **RESULT NAME** field names every asset the stage produces. It is a template: `{{variable}}` tokens are replaced with the current group's values, so each result is named after what made it.

```
{{name}}                 →  Anime Sorceress
{{name}} - NoBG          →  Anime Sorceress - NoBG
{{name}} - {{faces}}     →  Anime Sorceress - 300000
```

Use the **Insert variable…** dropdown to add a token without typing it. A live preview under the field shows what Group 1 resolves to. Leave the field empty and results fall back to `<group> · Stage N`.

### Parameter sources

Every parameter of the chosen workflow gets a source dropdown:

| Source | Meaning |
| --- | --- |
| **Manual value** | One fixed value, used by every group |
| **Variable · _name_** | Each group supplies its own value |
| **Output of _Stage N_** | Receives that stage's result from the same group |

Image and mesh parameters cannot be typed in, so they offer only the two sources that can carry a file: an **earlier stage's output**, or an **image / mesh variable** the groups fill in. A **boolean** input is equally strict the other way: it takes a boolean variable or a manual tick, and a boolean variable can only drive a boolean input — a toggle cannot fill a prompt, and text cannot fill a toggle. Everything else is manual or driven by a string/number variable.

The dropdown only lists variables that fit: an image input offers your image variables, a prompt offers your text and number ones. Retype a variable out from under a binding and the parameter says so instead of failing at run time.

When you pick a workflow, its parameters are pre-filled with the workflow's own defaults, and any image or mesh input is wired up for you — to the previous stage, or, for a first stage, to a variable of the matching type. Usually you only need to change the one or two parameters you actually want to vary.

Use the **‹** and **›** arrows in a stage header to reorder it. If moving a stage would leave a binding pointing at a *later* stage, that binding is cleared rather than left broken.

## Running the batch

**Run batch** is disabled until the configuration is complete. The amber bar above the workspace lists what is missing — click it to expand the list, click again to collapse it.

While a batch is running, the configuration is locked and the button becomes **Stop**.

### Execution order

The **ORDER** switch in the toolbar decides which way the run walks the grid. Both orders execute exactly the same cells and produce exactly the same results — only the sequence differs.

| Order | The run does | Best when |
| --- | --- | --- |
| **BY GROUP** | One group through every stage, then the next group | You want whole rows finishing, so a complete result exists early |
| **BY STAGE** | One stage across every group, then the next stage | **Speed.** ComfyUI keeps that stage's model loaded instead of unloading and reloading one at every stage boundary |

BY GROUP is the default, and is how batches ran before the switch existed. On a chain that mixes, say, an image model and a mesh model, BY GROUP makes ComfyUI swap models at *every* stage of *every* group; BY STAGE swaps once per stage for the whole batch, which on a long batch is the bigger saving by far.

A stage can only ever consume an **earlier** stage's output, so either order satisfies every binding: by the time a stage runs for a group, that group's previous stage has already finished.

The switch is **locked while the batch is running** — the walk is fixed when the run starts. Stop the batch to change it; **Continue** then finishes the outstanding cells in the new order.

If a stage fails, that cell is marked failed and the run moves on. Anything later in the *same* group that needed its output is reported as missing; other groups are unaffected.

You can leave the page. Open a result in an editor, visit another project, come back — the batch keeps running and the grid is still there when you return.

### Stopping and continuing

**Stop** is graceful, not instant. The stage that is already generating **runs to completion** — the button reads **Stopping after this run…** while it finishes — and its result is kept like any other. Everything still outstanding is marked **Cancelled**. Nothing is thrown away.

Once stopped, two buttons appear:

| Button | What it does |
| --- | --- |
| **Continue (_n_)** | Picks up where the run left off. Finished results are kept and skipped; the _n_ outstanding cells are run |
| **Restart** | Starts a completely fresh run of the whole grid. Earlier results stay in the project |

**Continue** keeps the original run, so its results land in the same cells of the same grid rather than starting a second one. Already-finished stages still feed the stages that depend on them, so a half-finished group carries on correctly instead of regenerating its earlier steps.

It also works after closing the project or reloading the app — the grid is rebuilt from the cards already saved, and **Continue** picks up from there.

Anything that is not finished is fair game for **Continue**, including cells that **failed** — so it doubles as a retry. If you edit the configuration while stopped, the changes apply to the cells that still have to run; work already finished is not regenerated. Add a group while stopped and **Continue** will pick it up too.

## Results

Switch to the **RESULTS** tab to see the grid: one **row per group**, one **column per stage** — the same axes as the configuration.

| Cell shows | Meaning |
| --- | --- |
| **Not run** | No result yet |
| **Queued** | Waiting its turn |
| **45%** | Running now |
| **Done** | Finished — the thumbnail is shown |
| _the error_ | The stage failed; hover the cell for the full message |
| **Cancelled** | Skipped because the batch was stopped |

Click any finished cell to open that asset in the Image Editor or Mesh Editor.

### Re-running one result

Hover a cell and a **delete** icon appears in its corner. Deleting a result empties that one cell — it goes back to **Not run** — and **Continue** then regenerates *just that cell*, leaving every other result untouched. Use it when one group came out wrong and the other nineteen are fine.

The card is removed from the batch; the generated file itself stays in your asset library, exactly like removing a result from a Kanban board. If later stages of the same group were filed as versions of what you deleted, their cells are emptied too — Continue rebuilds that part of the row.

The icon is hidden while a batch is running: a cell that is queued or generating owns its card until it settles.

Every result is a **normal card in the project**, carrying its asset exactly like any other generation — it shows up in your asset library and behaves like anything you made by hand. Results also survive a reload: reopen the project and the grid is rebuilt from the cards already there.

![image](http://localhost:3001/wiki-media/1786121108166-934021492.png)

### How results are filed

A result is stored **under whatever it was derived from**, so your library stays organised instead of filling with unrelated roots:

- An image made **from an image** (background removal, an edit pass) becomes an **edit** of that image.
- A mesh made **from a mesh** (simplify, texture, refine) becomes a **version** of that mesh.
- A mesh made **from an image** is a **new root mesh** — an image cannot be a mesh's parent.

If a workflow returns several outputs, only the **first** feeds the next stage; the cell notes how many extras were produced. All of them are still saved.

## Duplicating a batch

**Duplicate Project** creates a new Batch project with the same variables, groups and stages — and **none of the generated images or meshes**. Use it when you want to run the same pipeline on a new set of subjects without re-entering the whole configuration.

Any image or mesh a group *supplies* does travel with the copy: those are inputs to the recipe, not results of it, so the duplicate is ready to run rather than missing its files.

You are asked for a name, then taken to the new project.

## Saving, export and import

The configuration saves itself as you type; the toolbar shows **Saving…** then **Saved**.

A Batch project exports and imports like any other, as a **`.3dgp` bundle** — see **[Project export / import](37.md)**. The bundle carries the full recipe *and* the generated results, so a batch handed to someone else opens ready to run. Images and meshes picked for a variable travel with it too, and are re-pointed at their imported copies on the way in.

## Also reachable from an agent

The MCP server exposes the whole batch — `get_batch`, `update_batch` and `run_batch`, plus
`add_batch_groups` / `update_batch_group` / `remove_batch_groups` to edit one row at a time — so an
assistant can declare the variables, fill the group rows, wire the stage chain and run the grid
without the page being open. It speaks the same vocabulary you see here: a parameter's source is
`manual`, `variable:<name>` or `stage:<n>`, and a stage name is still a `{{variable}}` template.

`run_batch` behaves like **Continue** by default — a cell that already has a result is kept and
reused by the stages after it — and it can be limited to certain groups or stages, which is the
agent's version of re-running one cell. See **[MCP](39.md)**.
