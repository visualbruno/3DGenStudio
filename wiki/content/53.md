# Sprite Sheet

Bakes the effect you have open into a **flipbook** — a grid of frames on one PNG.

Click the grid icon in the toolbar.

## What it is for

An effect that costs four systems and two thousand particles here can cost **one quad** in a game once it is baked to a flipbook. It is also the only way to take an effect built in this editor into something with no particle system at all: a UI layer, a shader, a decal.

The trade is that a flipbook is a recording. It plays back from one angle and cannot react to anything.

## Before you open the dialog

**Frame the effect at its widest moment.** The camera does not move between cells, so anything that grows past the edge is cropped. Scrub to the biggest frame, set the view, then open the dialog — you can keep orbiting while it is open, and the camera is read when the bake starts.

## The options

| Option | What it means |
|---|---|
| **Start frame / End frame** | The range to sample. Each shows its time underneath. |
| **Columns / Rows** | The grid. Columns × rows is how many frames are captured. |
| **Cell size** | Pixels per cell — 64, 128, 256 or 512. |
| **Transparent background** | On by default. Off bakes black instead. |
| **Tone mapping** | On by default, matching the preview. |

Underneath, the dialog shows what those add up to: how many cells, how far apart the frames are in frames *and* seconds, the finished image size, and how long the sheet plays for.

## Transparent or black?

**Transparent** is right for most uses and is the default.

**Black** is right for an **additive** flipbook, because black adds nothing and the sheet then needs no alpha channel at all — the same reasoning as [Sprite Generation](/wiki/52).

## Tone mapping

Leave it **on** to get what the preview shows.

Turn it **off** if the engine will tone map its own frame — otherwise the effect is tone mapped twice and washes out. If you are baking a sheet for use as a texture inside another renderer, off is usually correct.

## Two things it will tell you

**Too large.** Over 8192 pixels on a side is refused. The limit is what an engine and a phone will accept, not what your GPU can do. Use a smaller cell size or fewer cells.

**Repeated cells.** If the frame range is shorter than the number of cells, several cells land on the same frame, which looks like the effect stalled. The dialog says so before you bake.

## Looping effects

For a looping effect the last cell deliberately stops **one step short** of the end frame, so cell N flows back into cell 1 with no stutter. A one-shot captures both ends of the range exactly. The dialog says which is happening.

## The result

A PNG named `<effect>-sheet-<columns>x<rows>.png`. The grid is in the filename because a flipbook is useless without it — whoever imports it has to tell the engine 4 by 4, and the image itself does not say so anywhere.

Cells run **left to right, top to bottom**, which is the standard convention and the one this editor's own flipbook expects.

## Playing it back here

To use a sheet inside the VFX Editor:

1. Assign it as the **Sprite Texture** on the Output node.
2. Add a **Sprite Sheet** block to Output and set columns and rows.
3. Add a **Play Sprite Sheet** block to Update.

Set its timing to `life` to play the sheet exactly once however long the particle lives — right for an explosion — or `rate` to play at a fixed speed and loop, which is right for a torch.

## Notes

The bake re-runs the simulation from the start with the effect's own seed, so it is reproducible: bake the same effect twice and you get the same image. Only the camera comes from your viewport.

Mesh emitters bake correctly — if a baked sheet ever looks emptier than the viewport, that is worth reporting.
