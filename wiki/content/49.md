# Trees

Grow a tree from a seed. Pick a species, roll the dice until the shape is right, and take away a game-ready mesh with bark UVs, foliage cards and wind data already baked in. Nothing is sculpted and nothing is downloaded — the whole tree comes out of about two kilobytes of numbers.

Trees are a **workspace of their own**, reached from **Trees** in the top navigation.

> Generation runs on the **Python mesh-tools service**. Configure it in **Settings → Mesh Tools**; the desktop app starts it for you.

## The tree is the spec

This is the one idea worth understanding before anything else, because everything on the page follows from it.

A tree is described by a **TreeSpec**: a small JSON document holding a seed and a few dozen numbers. That document *is* the tree. Feed the same spec in twice and you get the same mesh back, triangle for triangle. The GLB is not the asset — it is an output the spec can produce again at any time.

That is what makes the page's main loop possible:

- **Re-rolling costs nothing.** A new seed is a new tree, not an edit to an old one.
- **Nothing is destructive.** Every slider can go back where it was.
- **Saving a tree saves the spec.** It rides in the mesh asset's metadata, so a tree you made months ago can be reopened, re-rolled or nudged without keeping the mesh around.
- **Specs are files.** **Export spec** writes a `.tree.json` you can commit, diff, mail to someone, or drop into a build script.

## Two speeds

The page deliberately runs at two speeds, and knowing which is which explains why it feels the way it does.

**Moving a slider** regrows only the **skeleton** — the branch centre-lines, drawn as plain lines. It takes about a tenth of a second, so it can keep up while you drag.

**Generate mesh** builds the real thing: swept bark, foliage cards, UVs, materials. It takes about a second.

So the cheap thing is live and the expensive thing is a button. When a parameter that moves branches changes, the mesh on screen is dropped and you are back to the skeleton — because a mesh built from the previous numbers would be showing you something the panel no longer says.

## Species

Ten presets ship: **oak**, **pine**, **birch**, **poplar**, **willow**, **palm**, **bush**, **bonsai**, **sapling** and **dead**. Start from one. They are not decoration — a tree built from raw sliders almost always looks wrong, and each preset is a tuned set of about twenty values that a species actually needs.

Switching species **keeps your seed**, so you can grow an oak and a pine from the same number and compare them.

## How a tree is grown

Worth a paragraph, because it explains what the parameters do.

Branches are grown by **space colonization**. A cloud of *attraction points* is scattered inside the crown envelope; each point pulls the nearest branch tip toward it, and a tip that gets close enough consumes it. Branches therefore **compete** for the same space, which is what makes the result read as grown rather than drawn — a branch thins out where a neighbour already took the light.

The consequences you can steer:

| You want | Turn |
| --- | --- |
| A different silhouette | **Crown shape** — the single biggest lever |
| More or fewer branches | **Branch density** |
| A weeping tree | **Gravitropism** negative (Advanced) |
| Gnarled, storybook branches | **Randomness** up (Advanced) |
| Finer twigs | **Branch law exponent** down (Advanced) |

Branch thickness is not a slider per branch: it follows **da Vinci's rule**, where a limb is as thick as the limbs growing out of it, so a trunk is always consistent with the crown it carries.

## Parameters

Eight controls are visible by default. Roughly forty more sit behind **Advanced parameters**, grouped into **Skeleton**, **Branching**, **Foliage** and **Output**. Most trees never need them; the presets carry that complexity for you. Every control has a tooltip explaining what it does.

Sizes are **ratios of the tree's height**, not absolute measurements. Change **Height** alone and you get the same tree, bigger — nothing needs re-tuning.

## Foliage

Leaves are **cards** — flat quads carrying a leaf texture — and there are two things to know about them.

**Clusters, not single cards.** A cluster is a small fan of cards placed as one unit. It reads as a volume of leaves from any angle for a fraction of the cost, and it is the default because a leaf-per-twig tree runs to tens of thousands of cards and is unusable in an engine. **Leaf budget** is a hard cap: go over it and placements are thinned *evenly across the tree*, never chopped off one side.

**Normals are doing the work, not shape.** A flat card lit by its own flat normal looks like cardboard, and a canopy of them looks like a pile of cardboard. Leaf normals are instead pointed **outward from the crown centre**, so the canopy shades like the rounded mass it stands for. That single trick is most of why the foliage reads as foliage. It is the **Spherical normals** slider, and there is very rarely a reason to lower it.

For palms and conifers, **Align to branch** turns a leaf sticking out sideways into a frond running *along* its branch. A palm needs it near 1.

## Bark and UVs

Branches are swept tubes with **analytic cylindrical UVs** — the horizontal coordinate is the angle around the branch, the vertical one is distance along it. That is an exact answer rather than an approximation, so bark tiles perfectly and there is no reason to run **Auto UV** on a tree. **Bark UV tile** sets how much world length one tile of the texture covers.

### Junctions

Where a branch meets its parent, the two tubes simply **overlap** and the bark texture hides the join. It is free, it looks right, and it keeps the UVs exact.

If you need a genuinely **closed solid** — 3D printing, physics cooking, volume queries — switch **Junctions** to **Clean**. Every branch is boolean-unioned into one watertight surface. It costs about a second and the UVs are re-derived rather than exact, so use it when you need the solid and leave it alone when you do not.

## Textures

The **Textures** panel on the right has three slots. Each takes an image from your asset library (**Choose…**) or straight off disk (**Upload**); click a thumbnail to remove it.

| Slot | What it takes |
| --- | --- |
| **Trunk** | One tileable bark image. It repeats along every branch — **Bark UV tile** sets how much world length one repeat covers. |
| **Branches** | Optional. A second bark image for the thin wood. |
| **Leaves** | One *or more* leaf cut-outs, **with alpha**. |

### Leaves take a list, not an atlas

The renderer wants an *atlas* — one image holding a grid of leaf cut-outs that each card indexes into. That is the wrong thing to ask you for, because nobody has an atlas lying around; you have a few leaf PNGs. So hand over the PNGs and the generator builds the grid, fits each leaf into its cell without stretching it, and tells the cards how many cells actually hold a leaf.

That last part matters more than it sounds. Three leaves need a 2×2 grid, which leaves one cell empty, and a card that sampled the empty cell would alpha-test away and punch a hole in the canopy. The generator counts the real tiles and only draws from those, so any number of leaves works.

Three or four variants is plenty — with random per-card tile choice, rotation and tilt, a handful reads as a whole canopy.

### Branches are optional on purpose

Leave the **Branches** slot empty and the whole tree wears the trunk texture as **one bark material and one draw call**. Fill it and the bark splits in two, which costs a draw call — so it never happens behind your back. The split is by thickness: **Bark → split radius** (Advanced) sets how thin wood has to be before it counts as a branch.

### Generated from a prompt

These are ordinary image assets, so you can **generate them**. Produce a tileable bark from a species prompt and leaf cut-outs on a transparent background with the image tools, then pick them here — or pass them to the MCP tool as `trunkTextureAssetId`, `branchTextureAssetId` and `leafImageAssetIds`.

Procedural structure with generated surface is the combination worth reaching for: the shape is exact and reproducible, and the species is whatever you can describe.

> Leaf images need real transparency. A leaf on a white background comes out as a leaf on a **white card**, because the alpha channel is what cuts the card down to the leaf.

## Wind data

**Bake wind data** writes four values per vertex into the mesh's vertex colours, ready for a wind shader in Unity, Unreal or Godot:

| Channel | Meaning |
| --- | --- |
| **R** | Branch phase — a per-branch offset so limbs do not sway in unison |
| **G** | Stiffness — 1 at the trunk, falling to 0 at the tips |
| **B** | Leaf flutter phase — per-card randomness |
| **A** | Hierarchy weight — how deep in the tree this vertex sits |

**It is off by default, and the reason is worth knowing.** glTF defines vertex colour as a *multiplier on base colour*, so any spec-compliant viewer paints the tree with this data: the bark comes out green (its blue channel is always zero) and the foliage comes out as confetti. The numbers are correct — they are simply not colours. The Trees viewport ignores the tint either way, so the preview always shows you the material.

Turn it on when the tree is headed for an engine wind shader that samples vertex colour as data, and expect it to look wrong in Blender, in a glTF viewer, and in this app's other mesh views.

## Output

The pivot sits at the **base of the trunk**, which is where a scatter tool or a level editor expects to find it. **Engine preset** applies the axis and unit convention for your target — Unreal, for instance, means centimetres and Z-up.

**Download GLB** saves the mesh. **Save to library** stores it as a mesh asset with its spec attached; trees are global, like assemblies, and belong to no project, because a tree routinely mixes a bark texture from one project with a leaf atlas from another.

## Automation

The MCP server exposes the generator as `list_tree_presets`, `preview_tree_skeleton` and `generate_tree` — see **[MCP](39.md)**. The same generator also runs from the command line for batch work:

```
python -m app.services.treegen --preset oak --seed 7 -o oak.glb
python -m app.services.treegen --all -o forest/
python -m app.services.treegen --verify
```

## When a tree comes out wrong

**A bare pole with no branches.** The crown is out of reach. Raise **Attraction distance** or lower **Trunk clearance** so the trunk's tip can sense the crown.

**A shrub with no trunk.** **Trunk clearance** is near zero — which is exactly what the *bush* preset wants, and rarely what anything else does.

**Branches too coarse and blunt.** Lower **Growth step** (Advanced) for finer branches, and lower the **Branch law exponent** for finer twigs. Both cost generation time.

**A dense green ball with no visible structure.** The foliage is winning. Lower the **Leaf budget** or **Leaf size**, or press **Show skeleton** to check the branches underneath are actually good.

**Generation is slow.** **Branch density** and **Growth step** dominate the cost. The skeleton is capped so it cannot run away, but a tree asked for twenty thousand attraction points at a fine step will take its time.
